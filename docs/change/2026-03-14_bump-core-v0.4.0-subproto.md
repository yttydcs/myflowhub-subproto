# SubProto：对齐 Core v0.4.0

## 变更背景 / 目标
- `MyFlowHub-Core v0.4.0` 已发布，本轮需要将仍直接依赖 Core 的 8 个 `SubProto` module 统一对齐到该版本。
- 本次仅处理依赖升级与发布口径统一，不修改子协议 wire 语义与业务行为。

目标：
- 将 `auth/exec/file/flow/forward/management/topicbus/varstore` 升级到 `github.com/yttydcs/myflowhub-core v0.4.0`。
- 保持 `GOWORK=off` 下各 module 可独立拉取、独立测试、独立发布。

## 具体变更内容
- 依赖升级：
  - `auth/go.mod`、`auth/go.sum`
  - `exec/go.mod`、`exec/go.sum`
  - `file/go.mod`、`file/go.sum`
  - `flow/go.mod`、`flow/go.sum`
  - `forward/go.mod`、`forward/go.sum`
  - `management/go.mod`、`management/go.sum`
  - `topicbus/go.mod`、`topicbus/go.sum`
  - `varstore/go.mod`、`varstore/go.sum`
- 所有目标 module 的 `myflowhub-core` 版本统一从 `v0.3.0` 升级到 `v0.4.0`。
- 由于 `myflowhub-core v0.4.0` 要求 `go >= 1.25.0`，对应 module 的 `go` 版本声明同步提升到 `1.25.0`，并移除已不再需要的 `toolchain go1.24.5`。

## 对应计划任务映射
- `REM-1`：SubProto 8 个模块升级到 Core v0.4.0

## 关键设计决策与权衡
- 保持“多 module、分 tag 发布”策略不变：这比强行统一仓库版本号更容易维护现有下游依赖关系，也避免无关模块被动升级。
- 仅升级直接依赖 Core 的 module：控制变更面，减少额外测试矩阵与发布噪音。
- 接受随 Core 版本提升带来的 Go 最低版本提升：这是上游依赖约束，不单独做兼容性降级，避免后续再次出现工具链分裂。

- `cd flow; go test ./... -count=1` ✅
- `cd forward; go test ./... -count=1`（无测试文件，编译通过）✅
- `cd management; go test ./... -count=1` ✅
- `cd topicbus; go test ./... -count=1`（无测试文件，编译通过）✅

## 潜在影响
- 这些 module 的最低 Core 依赖提升为 `v0.4.0`，下游若锁定旧版 Core，将在依赖解析或编译时失败。
- 这些 module 的最低 Go 版本同步提升到 `1.25.0`。

## 回滚方案
- 回退本次提交并删除对应发布 tag。
- 若部分 tag 已被下游使用，需在回滚前先评估依赖影响，并优先通过新版本修复而不是复用旧 tag。
