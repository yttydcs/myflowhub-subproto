# SubProto：补齐剩余模块升级 myflowhub-core 到 v0.3.0

## 变更背景 / 目标
- Core `v0.3.0` 引入 Pipe 抽象（`core.IConnection.RawConn()` → `core.IConnection.Pipe()`），属于重大变更（Breaking Change）。
- 本仓此前已在部分模块完成依赖升级与测试适配（例如 `auth/management/varstore`），但仍有模块固定 `myflowhub-core v0.2.1`，导致仓库内部 Core 版本口径不一致，并在 `GOWORK=off` 下产生编译失败（测试 mock 未实现 `Pipe()`）。

目标：
- 将 `exec/forward/file/flow/topicbus` 统一升级到 `myflowhub-core v0.3.0`，并确保 `GOWORK=off go test` 通过。

## 具体变更内容
- 依赖升级（`v0.2.1` → `v0.3.0`）：
  - `exec/go.mod`、`exec/go.sum`
  - `forward/go.mod`、`forward/go.sum`
  - `file/go.mod`、`file/go.sum`
  - `flow/go.mod`、`flow/go.sum`
  - `topicbus/go.mod`、`topicbus/go.sum`
- 测试适配（不改子协议语义，仅满足接口变更）：
  - `exec/resp_ids_test.go`：mock connection 移除 `RawConn()`，新增 `Pipe()` 并使用 `nopPipe`。
  - `flow/resp_ids_test.go`：同上。

## 对应计划任务映射
- `SUBMORE0`：归档旧计划并建立新计划
- `SUBMORE1`：升级依赖到 Core `v0.3.0`
- `SUBMORE2`：`GOWORK=off` 回归测试

## 关键设计决策与权衡
- 不在测试中构造真实 TCP/底层连接：通过 `nopPipe` 最小实现满足接口，避免无必要 I/O 与不稳定依赖。
- 仅对需要编译通过的 mock 增补 `Pipe()`：不引入对子协议 payload 的额外解析与行为变更。

## 测试与验证方式 / 结果
在 `GOWORK=off` 下执行：
- `cd exec; go test ./... -count=1 -p 1` ✅
- `cd forward; go test ./... -count=1 -p 1` ✅
- `cd file; go test ./... -count=1 -p 1` ✅
- `cd flow; go test ./... -count=1 -p 1` ✅
- `cd topicbus; go test ./... -count=1 -p 1` ✅

## 潜在影响
- 这些模块的最低 Core 依赖提升到 `v0.3.0`；若下游强制锁定更低 Core 版本将发生依赖冲突或编译失败。

## 回滚方案
- revert 本次提交（依赖升级 + 测试 mock 适配）。
- 注意：若仓库其它模块已依赖 Core `v0.3.0`，回滚会重新引入“同仓不同 Core 版本”的问题，应整体评估后回退。
